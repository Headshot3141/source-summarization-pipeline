# Source Summarization Pipeline

This project is a template for turning long source documents, such as books or essay collections, into a standalone summary: `Summary.md` plus a PDF and an optional EPUB. One Claude Code session runs it by coordinating a team of agents. The summary has one part per source and one section per chapter. It aims for about 50% of the source's substantive word count and never goes over 55% without the user's approval.

The full process is in [plan.md](plan.md). A new session reads [status.md](status.md) first.

## Priorities and voice

Fidelity to the source comes first, then coverage of the main arguments, then clear prose, then style and word targets. Each source is condensed in its own order and in the author's voice, without "the author argues" on every line. Nothing from outside knowledge is added, and the source is reproduced as printed, errors included.

## Roles

The coordinator session sends out each agent with a prompt file generated by `Work/make_prompts.py`. Sonnet 5.5 writes the drafts. Opus 5.5 does every other job, so no agent reviews its own work. All agents share two rule files, [writing-rules.md](writing-rules.md) and [settled.md](settled.md).

## Key ideas

- **The preservation rule.** In earlier runs, the most common error made a summary sound more certain than its source. So hedges ("perhaps", "most"), contrasts ("but", "however"), conditions, attributions, framing words such as "suppose", and the evidence behind a kept claim must keep their full force. A minor point can be dropped whole, but a claim that stays can't lose its qualifiers. Losing one is a serious error, and the rule outranks the word budget.
- **Budgets and ceilings.** A draft aims at 40% of its unit's source words, within ±15%. Review may add up to another 10% where clarity or fidelity needs it. `Work/check_words.py` prints the running ratio after every batch and fails above 55%.
- **Report, then act.** An agent that notices a problem outside its job logs it instead of fixing it. The next pass, if the user wants one, works from that log.
- **Statuses.** Each unit is `pending`, `drafted`, `accepted` or `blocked`. Only the coordinator changes a status, with `Work/set_status.py`, after checking the output and its review record.

## The pipeline

1. **Preflight.** Inspect each source, usually a docling Markdown export of a PDF. Confirm the title and author from the title page. Record whether the summary should modernize old English, the typography rules, how to refer to each author, and the account's usage limits.
2. **Extraction.** A config file per source drives `extract.py`. It removes running heads, repairs ligatures and hyphenation, moves footnotes and marks block quotations. Uncertain repairs are logged and checked against the page, and OCR text is proofread.
3. **Splitting and budgets.** Chapters over 32KB are split into parts at sentence boundaries, with extra context added across each split. A check confirms the parts rebuild the chapter exactly. Each unit gets a draft budget (40% of its source words) and a ceiling (50%).
4. **Pilot.** One representative chapter goes through every step, and the user approves it before the full run.
5. **Summarization.** Sonnet agents draft the chapters in batches, starting with six at a time.
6. **Review.** A separate Opus reviewer with no earlier context corrects each draft. Its review record checks that contrasts, numbers and qualifiers survived. Scripts check word counts, fidelity and author naming before a chapter is accepted.
7. **Merge.** Split chapters are rejoined, and the joins are checked against the source.
8. **Assembly.** The accepted chapters and an introduction are combined into `Summary.md`.
9. **Independent verification.** Opus verifiers check a sample of chapters without editing them. Fix rounds then correct what they found.
10. **Later passes.** These are a style pass, targeted fix passes and an optional full pass. Each one saves a snapshot first, is tested on a few chapters if it can add words, and has every edit matched to a written record. Passes that add content are checked again independently. The user decides the length policy once, for all passes.
11. **Whole-document review.** Reviewers read the summary three chapters at a time for clarity only, with no fact-checking. An optional final check sends out agents to find errors, then has another agent try to disprove each finding.
12. **PDF.** The PDF is built once, at the end, and checked word for word against `Summary.md`.

## Where things live

Source documents stay untouched in `Sources/`. Extraction writes cleaned chapters to `Work/Chapters/`. Drafts go to `Work/Drafts/` and are kept unchanged. Reviewed summaries go to `Work/Summaries/`, and later passes edit those. Review records go to `Work/Reviews/`. Agent prompt templates are in [prompts.md](prompts.md), briefs for the later passes are in [passes/](passes/), and every check and its result is logged in `Work/checks.md`.

## Operations

`status.md` tells the next session where things stand. Each batch is committed with a progress count, usage is checked before each batch, and settled rulings go in `settled.md`.

## Why it's built this way

The rules come from earlier runs:

- Chapters that met their budgets still had serious errors: weakened hedges, lost contrasts and quotes credited to the wrong person.
- Agents "corrected" sources from memory.
- Agents use all the extra length they are allowed.
- Error-finding agents report far more problems than are real, so each finding is challenged before anything is fixed.
